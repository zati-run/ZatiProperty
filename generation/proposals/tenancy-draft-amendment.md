# Tenancy draft amendment — bounded E3 batch

Source baseline: df76fc7ffa63076af61dcd51e450121339a54826. Task coverage: T3.0 capability mapping, T3.1 protected draft amendment, T3.2 source/native/rendered verification, T3.3 independent review. These are subrequirements of ZP-5.1 and ZP-11.2, not E3 completion. No existing plan task is marked complete.

The domain already implements updateDraftTenancy, activateTenancy and endTenancy with actor/property scope, requestId idempotency, version CAS, immutable proposal revisions, audit and outbox. Reuse those actions. Do not add duplicate mutation APIs or weaken protected party/owner account membership gates.

Next journey: a manager opens an existing draft, reads its identity/current revision and complete current terms/parties, chooses Amend draft, reviews prefilled proposals, edits deliberately, then saves a new draft revision. Show the prior revision unchanged and the new version after reload. Bind tenancyId and expectedVersion from qualified selected-record context. A stale version must preserve entered values and require reload/review. Activation remains a separate explicit action. Existing active/ended records and legacy adoption are outside this amendment entry point; legacy adoption must retain its separate explicit authority/identity checks.

The source candidate adds only a read-only draftTenancyProposal contract. GET requires native read and updateDraftTenancy action grants without unsupported custom params, then manager-owned property scope; it returns only a validated current draft revision. It never initializes an audit head or writes a command receipt. Return: proposalVersion=1, tenancyId string, expectedVersion, revision, values(startDate/endDate/term/parties), and proposalDigest=SHA256(canonical envelope excluding proposalDigest). No requestId, reasonCode, adoption flag, internal child record IDs or private columns are prefilled. Domain candidate version0.1.4 remains uninstalled.

Required reusable Loom capability: an explicit constructor-qualified prefill tuple pinned to installed package/resource/read action, schema/content digests and scoped-proposal-v1. Server resolve fetches the proposal using the selected actor/role; validate exact tenancy identity and current expectedVersion against bound context. Only configured schema-valid editable fields may initialize the form; deny requestId, approval booleans, secret fields and arbitrary JS. Bind proposal digest/version into preparation and pending intent. Refetch/compare before preparation/submit so changed source proposals require review; preserve user edits and unknown-command recovery. A missing proposal or non-draft record disables editing while preserving receipt reconciliation. Never silently fall back to empty arrays for an existing draft.

The Loom author owns client context0.1.5 separately; no prefill capability exists in the inspected0.1.4 implementation. Therefore no generation-ready amendment template claiming prefill support is added yet. Once its exact supported schema is reviewed, add the native amendment template and bindings through the existing qualified helper. Place it alongside clearly labeled current revision/read-only history, not generic editable party/term tables.

Money/date copy: preserve actual existing currency; the current USD-only form cannot silently recast a non-USD draft. The prefill contract must either qualify the same currency's minor-unit scale or disable unsupported currency editing with a clear explanation. Explain exclusive end date as the first day outside the tenancy/term/party period. Keep date-only values stable across locale and reload. Explicitly label Save new draft revision and provide version/revision confirmation.

Verification: read contract zero writes, own/foreign manager and portal denial, current revision only, exact scalar whitelist, stable/changed digest, duplicate/malformed terms denial; adapter GET query handling and original amendment ACL; native readback and no audit-head initialization; UI prefill/version/source drift, preserved edits, duplicate/unknown recovery, original revision immutability, account binding denials, reload and narrow-width journey. No generation, live package acceptance or browser acceptance is claimed.

Remaining required work: native Sequence short codes; lease expiry/rent review date/nonnegative inspection frequency; operational open/closed/closed_allow_transactions transitions with protected accounting semantics; RFC5.9 rent-review approval and append-only effective rent versions; privacy-controlled files, communication, insurance, subsidy and CRM workflows. Lease renewal is RFC7.5/T4.1 with offer, human approval, signing and rent-version gates, not unrestricted active-tenancy editing.
