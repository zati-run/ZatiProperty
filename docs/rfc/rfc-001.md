# RFC-ZP-0001: ZatiProperty — A Loom-Generated Property Management System on NocoBase

Oct 9, 2026 · @David Ndungu · Revision 3

## 1. Abstract

ZatiProperty is a proposed property management system that agents MUST generate through the Loom MCP interface, entirely inside [NocoBase](https://github.com/nocobase/nocobase), the open-source no-code and AI platform. Each property management company installs and runs its own copy, so the system is single tenant. It covers the full operating loop of a rental business: prospects, leasing, tenancy, rent collection, maintenance, trust accounting, owner reporting, tax filing and AI-assisted automation. The code lives at [github.com/zati-run/ZatiProperty](https://github.com/zati-run/ZatiProperty).

Loom is the mandatory application construction interface. Everything ships as versioned desired-state artifacts applied through Loom to native NocoBase configuration and plugins: collections, pages, workflows and roles, plus server plugins for documented and version-verified Community Edition gaps and domain invariants, potentially including the ledger engine with trust controls, the audit trail, multi-factor authentication, document rendering and the payment and screening adapters. This RFC defines scope, architecture, domain modules, data model, API and AI integration, security, licensing and phased delivery. It replaces the earlier OpenProperty draft, which assumed a standalone multi-tenant application, and it keeps the feature taxonomy of RFC-2026-1024-REV2.

### Decisions in this revision

1. **Name.** The project is ZatiProperty. OpenProperty is retired.
2. **Platform.** ZatiProperty is built entirely on NocoBase, using only Community Edition features. It does not fork NocoBase core and does not depend on NocoBase commercial plugins.
3. **Tenancy.** One install serves one company. There is no tenant column and no row-level tenant isolation. Separation between staff, owners, tenants and vendors comes from NocoBase roles and data scopes.
4. **Gap filling.** Custom domain plugins require a documented CE gap or server-side domain invariant, a compatible license, and integration into the Loom-generated NocoBase application. Section 3.2 is a candidate gap register, not verified entitlement evidence.
5. **Construction.** Agents MUST use Loom MCP to generate and evolve the application. A standalone frontend, independent backend, direct database scaffolding, or manual builder session does not satisfy this requirement. Missing bridge capability blocks the affected task until an approved upstream Loom extension exposes it.
6. **Current scope.** This revision prepares instructions and the generation workflow only. It does not authorize connection to an arbitrary instance, endpoint enablement, live app creation, customer-data changes, external messages, payments, or deployment. No generated application is claimed by this document.

All capabilities below are product requirements or candidate mappings until backed by implementation and qualification receipts; present-tense domain descriptions do not claim delivery or CE entitlement.

**Key words.** The words MUST, SHOULD and MAY are used as defined in RFC 2119.

## 2. Motivation, Goals and Principles

### 2.1 Motivation

Commercial property management suites bundle accounting, leasing, maintenance and AI behind per-unit subscriptions and closed data models. Owners cannot audit how trust funds are handled, cannot move their data cleanly, and cannot extend the product. Existing open-source options cover fragments (rent tracking, maintenance tickets) but none offers compliant trust accounting, tax reporting and AI automation in one system.

NocoBase is the intended foundation for data modeling, native pages, access control, workflows and resource APIs. Availability and entitlements for each capability, including the runtime AI layer and MCP plugin, MUST be verified against the selected version and installed packages. Building on it means ZatiProperty writes custom code only for what is unique to property management and what the Community Edition lacks. A single-tenant design also matches how property managers adopt software: one company, one install, one database it controls.

### 2.2 Goals

1. **Full core loop on NocoBase.** The six domains (Tenant Management, Property Management, Leasing, Maintenance, Accounting, AI and Automation) map to NocoBase collections, pages, workflows and roles, with custom plugins only where the platform falls short.
2. **Ledger-first correctness.** All money movement is recorded in an immutable double-entry ledger with trust-fund segregation enforced in code and in the database, not by convention.
3. **Install in under an hour.** One Docker Compose file (NocoBase image, PostgreSQL, ZatiProperty plugins) yields a working install with default roles, a chart of accounts and optional demo data.
4. **Configuration as code through Loom.** Git holds declared desired state, stable logical IDs, dependencies and sanitized apply/readback receipts. Agents reconcile that state through discovered Loom MCP operations; plugin migrations implement only approved domain invariants or verified platform gaps.
5. **Multi-stakeholder by design.** Staff, owners, tenants and vendors each get role-scoped menus, data and fields.
6. **AI under the same rules as people.** NocoBase AI employees and its MCP server run inside role permissions; AI never posts to the ledger or decides an application.
7. **Customizable at the edges.** Extension fields, native pages and workflows are declared and applied through Loom. Reconcile existing operator builder edits as drift before applying new state. The locked ledger, audit and trust controls cannot be weakened through configuration.
8. **Localizable.** Currency, tax and jurisdiction rules are data and plugins. The v1 compliance focus is the United States.

### 2.3 Non-Goals

- **Multi-tenant hosting.** One install serves one management company. Hosting and redistribution rights require separate license qualification (section 3.3).
- **Forking NocoBase or requiring its commercial plugins.** ZatiProperty runs on the Community Edition as released.
- **Payments, banking, credit reporting or e-signature as a provider.** ZatiProperty integrates with them through adapters.
- **Legal advice.** Jurisdictional rule packs encode common requirements; operators remain responsible for compliance.
- **Native mobile apps and offline mode in v1.** Mobile use relies on NocoBase's mobile layout.
- **Property sales, brokerage and construction project management.**

### 2.4 Design Principles

| Principle | Meaning in practice |
| --- | --- |
| Configure before code | Use a NocoBase feature if one fits; write a plugin only for a documented gap |
| Community Edition only | No design depends on a paid NocoBase plugin |
| Ledger is truth | Balances are derived from journal lines; no mutable balance columns that can drift |
| Append, never edit | Financial and audit records are immutable; corrections are reversing entries |
| Core is locked, edges are open | Operators extend freely at the edges; the ledger, audit and trust controls cannot be reconfigured through the UI |
| Humans approve consequences | AI may draft, classify and recommend; money movement, evictions and adverse decisions need a human |
| Everything has an API | NocoBase generates a REST API for every collection; the interface uses the same API as integrators |
| Safe by default | A fresh install forces credential changes, enables MFA for financial roles and denies portal roles everything not explicitly granted |
| Open by default | Specs, schemas, tests and roadmap are public; no feature is withheld for a paid edition |

## 4. System Architecture

ZatiProperty is a set of plugins and configuration inside one NocoBase application backed by one PostgreSQL database. NocoBase's microkernel loads every feature as a plugin: server plugins extend a Koa-based HTTP server and a Sequelize data layer, and client plugins extend the React interface. ZatiProperty adds its domain plugins on that foundation, and one installation serves one company.

```text
Versioned ZatiProperty desired state
    -> agent using scoped Loom MCP endpoints
    -> one NocoBase CE application
    -> native collections, roles, pages, workflows and approved domain plugins
    -> one company database and file store
```

Each role signs in to the same NocoBase application; ZatiProperty's three plugin groups sit on NocoBase's own services, and all data stays in one PostgreSQL database and one file store.

### 4.1 Architectural Rules

1. **Configure before code.** If a NocoBase feature fits, use it. Custom code needs a gap listed in section 3.2 or a domain rule NocoBase cannot express.
2. **Rules that touch money, compliance or permissions live on the server.** They are enforced in plugin services and in the database, never only in the interface or in a no-code workflow an operator could edit.
3. **One door to the ledger.** Journal entries are written only through the ledger service. Direct create, update and delete on ledger collections MUST be denied to application roles outside the posting service. Privileged operators and database administrators remain a separate trust boundary; application controls cannot make their access impossible.
4. **Configuration is code.** Collections, roles, workflows and pages are declared in Git, then applied and read back through Loom. Reconcile operator edits before the next apply. A complete lossless export is not assumed; maintain desired state and resolved bindings even when native blueprint export is unavailable.
5. **Money is integer minor units** plus an ISO 4217 currency code. Floating point is forbidden for amounts.
6. **Ports for external systems.** Each external system sits behind an interface with at least one adapter and a fake for tests.
7. **Every request has an actor.** Users, API keys and AI employees are NocoBase roles with explicit permissions, and every state change is attributed in the audit log.
8. **Keep the domain core portable.** The ledger and rule engines are plain TypeScript packages with no NocoBase imports. Plugins are thin wrappers, so platform upgrades touch little code.

### 4.3 Single-Tenant Model

- One company, one database, one file store. Backups, upgrades and encryption keys are per install.
- Roles: staff roles, `owner`, `tenant`, `vendor`, and roles for AI employees and MCP clients.
- Separation among owners, among tenants and among vendors is enforced by NocoBase access control: menu and route permissions, collection actions, field permissions and data scopes. This is an application-layer control, unlike database row-level security. ZatiProperty therefore runs an automated role-by-collection-by-action test matrix and treats any gap as a release blocker (sections 13 and 14).
- A company's own books versus client trust funds, or several legal entities, are ledger funds and dimensions, not tenants (section 9.1).

### 4.6 Mandatory Loom Construction Contract

The agent MUST load `.agents/skills/zatiproperty-loom/SKILL.md` and follow `docs/generation/README.md` before application work. Loom is the build-time bridge; NocoBase owns execution, persistence, native rendering and permissions. No separate React app, backend service or direct SQL schema is an acceptable substitute for generating the app through Loom. Custom domain plugin development is permitted only for a recorded CE gap or server invariant, with its collections/actions/UI wired into the generated NocoBase application. If Loom cannot perform a required construction operation, stop that operation and qualify an upstream bridge extension before continuing it.

The source baseline in Loom's README and delivery guides 004 and 005 establishes three different surfaces:

| Endpoint | Construction capability and boundary |
| --- | --- |
| `/mcp` | Bounded read-only collection access. It cannot generate the app. |
| `/ui/mcp` | Disabled by default. Seven typed tools for a limited native UI subset: get, catalog, apply blueprint, compose, configure, reaction metadata and supported block rules. Its credential authorizes the whole bound application and does not inherit read-endpoint collection, field or tenant restrictions; typed operation limits are not a resource isolation boundary. It is not a general schema/role/workflow authoring interface. |
| `/native/mcp` | Disabled by default. Broader catalog depends on the backend version, installed packages, role and pinned catalog. May include model, record, role, workflow, script and administration writes. Requires explicit authority, separate client/backend credentials and an approved catalog. Read-endpoint field/scope restrictions do not carry over. |

Tool counts in source fixtures are not a promise about the target. Discover every page of the current tool catalog and use the returned schemas; never invent names, payloads or guarantees. A catalog drift failure requires reviewed recapture and restart, not permission broadening or an alternate write path. Discovery proves exposure, not execution permission, CE entitlement or functional correctness. Provision credentials through operator-managed secret references; never put them in Git or receipts.

### 4.7 Generation Lifecycle and Acceptance

1. **Qualify target and authority.** Establish the owner-approved NocoBase instance, environment, Loom revision, NocoBase/plugin versions, selected role, endpoint credentials and operation boundary. Record CE/license evidence and resource limits. Preparation alone authorizes no live generation. Inspect existing app state before planning changes; protect unrelated and operator-authored objects.
2. **Discover and map.** Enumerate the actual MCP tool catalog and schemas and read relevant native collections, relations, roles, pages, workflows and plugins. Map each RFC requirement to an exposed capability, a documented domain plugin, or a blocker. Record unsupported calls, upstream gaps and unqualified renderers explicitly.
3. **Declare desired state.** Store reviewable artifacts under `generation/`: `app.yaml`, `collections/`, `roles/`, `pages/`, `workflows/`, `plugins/`, `fixtures/` and `bindings/`. The manifest declares namespace ownership, dependency order, versions and stable logical IDs such as `zp.tenancies`. Domain names in this RFC are logical names, not a mandated physical prefix. Bind logical IDs to returned native identifiers, preserving existing identifiers and preventing collisions. No artifacts are claimed to exist merely because this RFC names them.
4. **Plan and review differences.** Compare observed and desired state, record additions/updates/deletions and permission changes, and delimit the authorized batch. Planning/diff is an agent workflow, not an assumed universal Loom tool or server dry-run feature. Destructive changes, scripting, plugin operations, role escalation, external side effects and production financial actions need their specific authority; a generation request is not a blanket grant. Use backups/recovery appropriate to the change and preserve unrelated data.
5. **Apply through Loom.** Apply authorized dependency-ordered changes using only discovered, schema-valid tools. Default fixtures to synthetic records and keep external delivery/payment actions disabled. Record sanitized inputs or hashes, tool/schema identity, returned object IDs and outcome. Tool success alone does not close acceptance.
6. **Read back and reconcile.** Retrieve actual native state through the appropriate Loom tools, compare it with desired state, and save bindings and sanitized receipts under `docs/generation/receipts/`. A timeout or unknown mutation outcome MUST NOT be replayed blindly. Inspect current state and determine whether it applied before a scoped retry. Do not assume transactional apply, idempotency, complete blueprint export or rollback exists for every operation.
7. **Prove the generated app.** Check native page rendering and role navigation in NocoBase, record persistence after reload, relationship integrity, workflow behavior, allowed and denied role operations, field/data scopes and protected ledger access. Capture exact source, target versions, object bindings and evidence. Browser observation validates rendering; it is not an alternate construction path. Distinguish source checks, MCP readback, native UI evidence, provider tests and production acceptance.
8. **Close or checkpoint.** Record completed requirements, remaining gaps, uncertain outcomes and recovery next steps. Repeat discovery and reconciliation when versions/catalogs change. Missing capability or required acceptance leaves that requirement blocked; it cannot be replaced by a static screen or an off-platform prototype.

Loom construction credentials are never tenant/owner/vendor credentials and are never reused for the runtime AI assistant. Application generation does not authorize live ledger posting, fund transfers, applicant decisions, messaging, or activation of consequential automations. Those remain governed by the domain services, human approvals and explicit operational authority below.

## 5. Module: Tenant Management

This module owns everything about the people who rent: from the first inquiry to move-out. Its central record is the **tenancy**, which links one or more tenants to a unit for a period of time.

### 5.1 Tenancy Record

| Attribute | Description |
| --- | --- |
| Short code | Unique, human-friendly identifier per installation (a NocoBase Sequence field), usable in search, imports and payment references |
| Parties | One or more tenant contacts with a designated primary; guarantors and occupants as separate roles |
| Dates | Start, optional end, lease expiry, next rent review, inspection frequency in months |
| Status | `open`, `closed`, `closed_allow_transactions` (closed but still accepts late postings such as refunds and final charges) |
| Rent schedule | Versioned rent changes with effective dates; history is never overwritten |
| Deposit ledger | Security deposit and bond held, with jurisdictional holding and interest rules applied from rule packs |
| Extra charges | Recurring non-rent charges such as parking, pet rent, utilities, each with its own income account |
| Custom fields | Company-defined typed fields added to the tenancy, contact and property collections with NocoBase's data model tools |
| Attachments and letters | Documents, mail-merged notices, and a communication history tied to the tenancy |

### 5.2 Rent Collection

- A scheduler generates charges ahead of each due date from the tenancy's rent schedule and recurring charges. Generation MUST be idempotent per tenancy, charge type and period.
- Payments arrive through a payment adapter (ACH, card, or recorded cash and check) and are posted to the ledger as receipts into trust.
- **Allocation.** Each payment is applied to open charges by a configurable order (for example: oldest first, or by category priority such as deposits, then rent, then fees). Overpayments become tenant credit.
- **Autopay and payment plans.** Tenants may enroll in autopay and request plans; plans are agreements that change expected dates without deleting the original charges.
- **Late fees.** Grace days, flat or percentage amounts, daily or one-time, and a jurisdictional cap come from configuration and rule packs. Fees are separate charges, never edits to rent.
- **Returns.** An ACH return or card dispute posts a reversing entry, re-opens the charges and fires a `payment.returned` event.
- Receipts and monthly statements are generated automatically and visible in the tenant portal.

### 5.3 Tenant Communication

- Threaded conversations between staff and tenants across email, SMS and in-app, unified in one timeline per tenancy.
- Templates with merge fields; bulk announcements by property, building or tenancy filter; delivery and read status.
- SMS MUST honor opt-in and opt-out state and quiet hours; the platform stores the consent record.
- Mail-merge letters (notices, rent increase letters, inspection notices) are generated as documents, attached to the tenancy and optionally sent by a print-and-mail adapter.

### 5.4 Renters Insurance

- Leases can require renters insurance with minimum liability limits. The module tracks policy carrier, number, coverage dates and the additional-insured status of the landlord.
- Verification occurs by document upload with staff review, or by a carrier adapter that returns policy status.
- Reminders are scheduled ahead of lapse; a lapse creates a task and optionally a charge for a master or force-placed policy where lawful.

### 5.5 Tenant Screening

- Screening is performed by external consumer reporting agencies through adapters (credit, criminal, eviction history, income and identity verification).
- The applicant's written authorization MUST be captured before any report is requested.
- Screening criteria are defined once per company or property and applied uniformly; the system records which criteria produced which outcome.
- An adverse decision triggers the notice workflow required by the Fair Credit Reporting Act, with the reporting agency's contact details and the applicant's dispute rights. See section 13.
- Raw reports are stored encrypted, access-logged, and purged on a configurable retention schedule.

### 5.6 CRM (Prospects)

- Prospects are created from listing inquiries, website forms, phone calls or manual entry, with source attribution.
- A configurable pipeline (inquiry, showing scheduled, toured, applied, approved, lease signed, lost) with follow-up tasks and reminders.
- Showing scheduling with self-serve slots and calendar sync.
- A prospect converts to an applicant and then a tenant without re-keying data.

### 5.7 Subsidizer (Subsidized Housing)

- Models housing assistance programs (for example voucher programs): the subsidy agency, contract number and dates, and the split of each month's rent between the tenant portion and the agency portion.
- Tracks recertification due dates and required inspections, and raises tasks ahead of deadlines.
- Agency payments are reconciled against expected amounts; shortfalls surface as a distinct receivable rather than as tenant arrears.
- Program rules (payment standards, utility allowances) are data in a rule pack, not code.

### 5.8 Events Emitted

`tenancy.created`, `tenancy.closed`, `charge.generated`, `payment.received`, `payment.returned`, `late_fee.assessed`, `insurance.lapsed`, `screening.completed`, `prospect.converted`, `recertification.due`

### 5.9 Rent Reviews

A scheduled workflow finds tenancies whose next rent review date falls inside a configurable lead time, or on an account-wide interval, and creates a review task for the manager. The manager picks one of three outcomes: postpone the review to a new date, maintain the current rent (recorded, with the next review date advanced), or change the rent. A change creates a new rent version with an effective date, generates the notice letter, and checks the applicable rule pack for notice periods and caps before the notice can be sent.

## 6. Module: Property Management

This module defines the physical and organizational hierarchy and gives owners, managers and field staff the views and tools to run it.

### 6.1 Hierarchy

```
Organization
  Portfolio            (a grouping for reporting and access; often one per owner or strategy)
    Property           (an address or campus; has an owner or owners via ownership shares)
      Building         (optional)
```

A property has one or more **ownership shares** that sum to 100%, which drive distributions and statements. A unit can have any number of tenancies over time but only one active primary tenancy at once unless the property is flagged for per-room leasing.

The leasing module shortens vacancy by turning a listing into a signed lease with as little manual work as possible. The path is: publish, inquire, apply, screen, decide, sign, activate.

## 8. Module: Maintenance

Maintenance connects tenants who report problems, managers who triage them, vendors who fix them and the ledger that pays for them.

### 8.1 Maintenance Requests

- Tenants submit requests in the portal, mobile app, by email or SMS, with category, description, photos or video, preferred times, permission to enter and pet information. Staff can also log requests by phone.
- Triage assigns priority (`low`, `medium`, `high`, `urgent`). Keyword and category rules flag emergencies such as gas smell, flooding or no heat in winter, and notify on-call staff immediately.
- Duplicate detection groups requests about the same issue in the same unit or building.
- A request becomes a **work order** by one action, carrying over all fields and attachments. Requests can also be closed with a reply without creating work.

### 8.2 Work Order Lifecycle

Every work order has one of five canonical states. Organizations MAY rename labels but cannot remove states.

| State | Meaning | Exits to |
| --- | --- | --- |
| New job | Created, not yet assigned or quoted | Quote, Progress, Closed (cancelled) |
| Quote | One or more vendors asked to bid, or an estimate awaiting approval | Progress, New job, Closed (cancelled) |
| Progress | Work approved and underway or scheduled | Complete, Quote |
| Complete | Work finished, awaiting invoice and payment | Closed, Progress (rework) |
| Closed | Paid and settled, or cancelled | Reopen creates a linked work order |

Work order fields include property, unit, tenancy, assigned vendor, priority, estimated value, on-site contact name and phone, scheduled window, invoice number, invoice date and invoice amount. A work order may carry multiple quotes, but only one is awarded.

### 8.3 Quotes and Approvals

1. A manager sends a request for quote to one or more vendors from the preferred list.
2. Vendors reply in the vendor portal or mobile app with amount, scope, availability and attachments.
3. The manager compares quotes side by side and awards one.
4. If the estimate exceeds the property owner's approval limit, the work order is routed to the owner portal for a decision before moving to Progress. The decision and its timestamp are recorded.

### 8.4 Vendor Management and Vendor Portal

| Capability | Detail |
| --- | --- |
| Vendor profile | Business name, trades, service area, contacts, payment terms, preferred status, internal rating |
| Compliance documents | W-9, certificate of insurance, license; expiry dates tracked, expired vendors blocked from new awards |
| 1099 flag | Marks vendors whose payments are reportable; feeds tax preparation (section 9.5) |
| Vendor portal | Assigned jobs, quote submission, scheduling, status updates, completion photos, invoice upload, payment status and message thread |
| Performance | Response time, completion time, rework rate and spend by vendor |

### 8.5 Payment Binding

Maintenance expenses MUST be paid through the work order. Paying a vendor invoice creates a payable against the work order, and the payment posts to the ledger against the owner's or property's expense account with the work order as the reference. A direct vendor payment outside a work order requires an explicit manual-expense permission and is flagged in the audit log. This keeps accounts payable, the cashbook and the general ledger synchronized.

### 8.6 Preventive and Recurring Work

- Recurring schedules (filter changes, HVAC service, inspections, seasonal tasks) generate work orders ahead of due dates per unit, building or property.
- Inspection findings in the mobile app can create work orders directly, with photos attached.

## 9. Module: Accounting

Accounting is the part of a property management system that cannot be wrong. It is built on one immutable double-entry ledger; every other financial feature is a view or a workflow on top of it.

### 9.1 Ledger Model

- **Chart of accounts** per installation, seeded from templates (residential, commercial, mixed) and editable. Account types: asset, liability, equity, income, expense.
- **Journal entries** contain two or more lines whose debits equal credits, in the same currency. An unbalanced entry cannot be committed.
- **Funds.** Each ledger account belongs to a fund: `trust`, `operating` or `reserve`. Client money lives only in trust accounts; the management company's own money lives in operating.
- **Dimensions.** Each line can carry property, unit, tenancy, owner, vendor and work order references. Sub-ledgers (tenant ledger, owner ledger, vendor ledger) are queries over these dimensions, not separate tables.
- **Immutability.** Posted entries are never updated or deleted. A correction is a reversing entry plus a new entry, each linked to the original and explained.
- **Basis.** The same ledger produces cash-basis and accrual-basis reports. Owner statements default to cash basis.
- **Periods.** Accounting periods can be soft-closed (warn on posting) or hard-closed (reject); reopening a period requires a permission and is audited.

### 9.2 Trust Accounting Controls

These controls are enforced in code by the ledger service and are covered by property-based tests.

| Control | Rule |
| --- | --- |
| Receipts into trust | Tenant funds settle into a trust account before they are available for distribution, fees or payment to anyone |
| No commingling | Operating-fund accounts cannot appear in the same entry as owner funds except through a typed transfer entry such as a management fee |
| No negative owner balance | A disbursement for an owner cannot exceed that owner's available balance after reserves and unsettled funds |
| Deposit segregation | Security deposits post to deposit liability accounts and, where the rule pack requires, to a separate bank account |
| Settled funds only | ACH and card receipts become distributable only after the configured settlement and return window |
| Three-way reconciliation | Bank statement balance, trust ledger balance and the sum of all owner, tenant and deposit sub-ledgers must agree at each period close; a mismatch blocks hard close |
| Dual control | Distribution runs and manual journal entries above a configurable amount require a second approver |

### 9.3 Owner Distributions

1. At the scheduled run date the system computes, for each owner, collected income minus expenses paid, management fees, and the required reserve.
2. It produces a draft distribution run showing each owner's amount, any holds (insufficient funds, missing payout details, expired W-9) and the statement preview.
3. An authorized user reviews and approves the run.
4. Approved amounts are paid through the payment adapter (ACH or check file) and posted to the ledger; owner statements are published to the portal.

Fees are posted before distributions in the same run so statements show the full calculation (section 6.4).

### 9.4 Bank Connections and Reconciliation

- A banking adapter (for example an account aggregation service) imports transactions daily; OFX, QIF and CSV import are always available as a fallback.
- A matching engine pairs bank transactions with ledger entries using amount, date window, reference and learned rules, and proposes matches for review.
- Unmatched items land in a queue with suggested actions (create entry, match to batch, flag).
- Reconciliation produces a signed, immutable reconciliation report per bank account and period.

### 9.5 1099 Preparation and IRS IRIS Filing

- The system accumulates reportable payments by payer entity, payee and tax year. Vendors flagged for 1099 and owners receiving reportable rent are included automatically.
- Payee tax information is collected through a W-9 request flow with TIN validation hooks. Missing or mismatched TINs block filing and generate follow-up tasks.
- Form types, box mappings, reporting thresholds and filing deadlines live in a versioned tax rule pack because they change by tax year. Thresholds MUST NOT be hard-coded; the rule pack for each year is verified against current IRS instructions before release.
- Output: recipient copies (PDF, portal delivery), IRS-ready data files, and an adapter for the IRS Information Returns Intake System (IRIS). Direct filing requires the operator to hold their own transmitter credentials with the IRS; ZatiProperty provides the adapter, but it does not file on anyone's behalf.
- Corrections and voids are first-class and traceable to the original submission.

### 9.6 Tax Templates

Tax templates map chart-of-accounts categories to report lines, for example the expense categories on a landlord's annual tax schedule. Organizations can clone and customize templates, and the year-end owner package uses them to produce a tax-ready summary per owner and property.

### 9.7 Financial Reports

| Category | Reports |
| --- | --- |
| Tenant | Tenant ledger, aged receivables, delinquency, rent roll, deposit register |
| Owner | Owner statement, owner ledger, distribution history, year-end package |
| Property | Income statement, balance sheet, cash flow, 12-month trend, vacancy, lease expirations |
| Vendor | Vendor ledger, payables aging, 1099 summary |
| Control | Trial balance, general ledger detail, trust bank reconciliation, unreconciled items, audit trail export |
| Company | Management fee income, company income statement and balance sheet (operating funds only) |

All reports run on documented SQL views, support date and basis parameters, and export to CSV, XLSX and PDF. Reports can be saved, shared by role and scheduled for email delivery.

### 9.8 Company Financial Summary and General Ledger Management

- The management company's own books (fee income, payroll, rent, software) live in operating accounts and are reported separately from client funds. A company financial summary shows revenue by fee type, expenses and margin per portfolio.
- General ledger management covers chart-of-accounts editing with merge and retire (never delete used accounts), manual journal entries with approval, recurring entries, and account mapping to reports and tax templates.

### 9.9 Audit Trail

- The audit log is append-only and hash-chained: each record includes the hash of the previous record, so tampering is detectable by a verification job.
- Each record stores actor type and id, installation reference, action, entity type and id, before and after values for changed fields, request id, source IP, and for AI-originated actions the model, prompt reference and approving user.
- Audit data is exportable, retained per policy, and visible in the UI to users with the audit permission.

## 10. Module: AI and Automation

AI in ZatiProperty is optional, provider-agnostic and bounded by the same permissions and audit rules as a human user. Turning it off MUST leave every non-AI feature fully working.

### 10.1 AI Gateway

- All model calls go through one gateway port with adapters for hosted model APIs and for self-hosted models behind an OpenAI-compatible endpoint. Organizations choose their provider, and can keep all data on their own infrastructure.
- Per-installation controls: enabled features, allowed providers, monthly spend cap, data-redaction level (mask names, contact details and account numbers before leaving the deployment), and an emergency kill switch.
- Retrieval over company data starts with PostgreSQL full-text search through the approved policy-search plugin, scoped by native role and entity permissions. Vector retrieval is a separately qualified extension, not an assumed CE capability.
- Prompts are versioned files in the repository with an offline evaluation suite; a prompt change that regresses the suite does not ship.

### 10.2 Autonomy Levels

| Level | Behavior | Examples |
| --- | --- | --- |
| 0 Suggest | Shows a recommendation; the user performs the action | Suggested vendor, suggested reply |
| 1 Draft | Prepares the action; a human reviews and sends or approves | Draft owner message, draft renewal offer, drafted work order |
| 2 Act within limits | Executes low-risk actions inside configured limits and logs them | Categorize and prioritize a request, send a status update, schedule a reminder |
| 3 Prohibited | Never performed by AI | Moving money, posting or reversing ledger entries, approving or declining applicants, sending legal notices, starting eviction steps, changing permissions |

Level 3 is enforced at the tool layer: those tools simply do not exist for AI actors.

### 10.3 Assistants

- **Assistant (staff).** A conversational interface inside the app that answers questions over the organization's data ("which tenants are more than 30 days late at Maple Court?"), drafts messages and work orders, and runs reports. Answers show the records they came from.
- **Chat (tenants and owners).** A scoped conversational interface in the portals and mobile app for balances, payment help, maintenance reporting, lease questions and statement explanations. It can only see the signed-in person's own data and hands off to staff when it cannot answer.

The proprietary product names used by commercial platforms are not reused.

### 10.4 Domain AI Engines

| Engine | Function | Hard limits |
| --- | --- | --- |
| Maintenance AI | Classify requests, set priority, ask tenants clarifying questions, read photos, suggest vendors and likely scope | Emergency keywords always notify a human regardless of model output |
| Work Order AI | Draft scope of work, summarize and compare quotes, extract invoice fields and match them to the quote, flag unusual amounts or duplicates | Cannot award, approve or pay |
| Lease Renewal AI | Predict renewal risk, recommend term and rent options within configured rules, draft the offer | Cannot send offers or exceed legal caps from the rule pack |
| Rental Applications AI | Check completeness, extract data from uploaded documents, summarize verified facts against the written criteria | MUST NOT recommend approval or denial, and MUST NOT use or infer protected characteristics |
| Tenants Insurance AI | Read policy documents, verify coverage against lease requirements, chase lapses | Verification result is a suggestion until staff confirm |
| Policy Handbook | Organization policies and procedures are ingested; assistants cite the policy text they used | Cites only uploaded policies, never invented ones |

### 10.5 Safety and Fair Housing

- Tenant- and applicant-supplied text is untrusted input. Prompts separate instructions from data, and tools never execute instructions found inside records, emails or documents (a defense against prompt injection).
- Applicant-facing automation follows the written criteria only, treats every applicant the same, and logs the criteria version used.
- Every AI output that affects a person is stored with its inputs, model and version for review. Users can correct an AI result and the correction is kept as evaluation data (with consent in hosted deployments).
- Quarterly bias and quality evaluations are published for the default prompts.

### 10.6 Model Context Protocol (MCP) Server

This section specifies the future runtime property-management AI interface. It is separate from the Loom construction endpoints in section 4.6. The illustrative domain tools below are requirements, not discovered Loom tool names or evidence that the selected NocoBase CE instance exposes them. Runtime roles never inherit authoring credentials.

ZatiProperty intends to use NocoBase's runtime AI/MCP capabilities with approved domain tools, so external assistants operate under the same native permissions as users. Qualify availability and entitlements on the pinned CE release; missing runtime capabilities remain blocked or require an approved domain plugin. This does not introduce a standalone application or reuse Loom's broad construction catalog.

| Aspect | Specification |
| --- | --- |
| Transports | Streamable HTTP for remote use; stdio for local development |
| Authentication | Pinned NocoBase runtime authentication with explicit company-admin approval of each client, scoped credentials and revocation; OAuth/PKCE support requires separate qualification |
| Authorization | Each token maps to an RBAC role and an entity scope (portfolio, property or owner); the server filters resources and rejects out-of-scope tool calls |
| Resources | Read-only documents such as properties, units, tenancies, ledgers, work orders, statements, the policy handbook, and the OpenAPI description |
| Tools | Typed functions with JSON schemas, each marked `read`, `write` or `proposal` |
| Prompts | Reusable workflows such as monthly delinquency review, vacancy turn checklist and owner update draft |
| Audit | Every call is logged with the client, token, tool, arguments, result summary and any approving human |
| Limits | Per-token rate limits, result size limits and an installation-wide pause switch |

Example tools:

| Tool | Type | Description |
| --- | --- | --- |
| `search_tenancies` | read | Find tenancies by name, unit, status or balance |
| `get_tenant_ledger` | read | Charges, payments and balance for a tenancy |
| `list_work_orders` | read | Filter by property, status, priority, vendor |
| `run_report` | read | Execute a named report with parameters |
| `create_maintenance_request` | write | Log a request for a unit on behalf of an authorized user |
| `draft_message` | proposal | Prepare a tenant or owner message for human review |
| `propose_work_order_award` | proposal | Recommend a vendor with reasons; a human approves |
| `propose_late_fee_waiver` | proposal | Recommend a waiver with justification; a human approves |

`write` tools are limited to low-risk records. Anything with financial or legal consequence is a `proposal` that appears in an approval inbox in the app; the MCP server has no tool that posts to the ledger, disburses funds or decides an application.

### 10.7 Automation Engine

Beyond AI, a rules engine lets organizations define triggers (events from section 4), conditions and actions without code, for example "when a rent payment is returned, create a task for the property manager and send the tenant a notice template". Rules are versioned, testable in a dry-run mode, and subject to the same audit and permission checks.

## 11. Data Model

The schema MUST be expressed as versioned desired-state collections, fields and relations and generated through Loom into the pinned NocoBase main data source. NocoBase manages its native identifiers, metadata and migrations. Database-level ledger/audit constraints belong to approved domain plugin migrations, not an independently applied SQL application schema. The prior standalone UUID/organization/RLS schema is superseded.

### 11.1 Entities by Module

| Module | Logical collections or platform services |
| --- | --- |
| Platform | `company_settings`, NocoBase users/roles/API credentials, `audit_log`, `event_outbox`, `documents`, `notifications`, `settings`, `rule_packs` |
| Property | `portfolios`, `properties`, `buildings`, `units`, `owners`, `ownership_shares`, `management_agreements`, `fee_schedules` |
| Tenant | `contacts`, `tenancies`, `tenancy_parties`, `rent_versions`, `recurring_charges`, `charges`, `payments`, `payment_allocations`, `deposits`, `insurance_policies`, `messages`, `subsidy_contracts` |
| Leasing | `prospects`, `listings`, `applications`, `screening_requests`, `leases`, `lease_templates`, `signature_envelopes`, `renewal_offers` |
| Maintenance | `maintenance_requests`, `work_orders`, `quotes`, `vendors`, `vendor_documents`, `inspections`, `recurring_work_schedules` |
| Accounting | `ledger_accounts`, `journal_entries`, `journal_lines`, `bank_accounts`, `bank_transactions`, `reconciliations`, `distribution_runs`, `statements`, `tax_forms`, `tax_templates`, `periods` |
| AI | `ai_actions`, `ai_proposals`, `embeddings`, `policy_documents`, `mcp_clients` |

### 11.2 Collection and Invariant Contract

One installation serves one company. There is no `organizations` tenancy model, `org_id` column, cross-company membership service or database RLS tenant scheme. Company settings are an installation singleton; owner, tenant, vendor and staff separation uses verified NocoBase roles and data scopes. Business legal entities remain ledger dimensions where required.

| Domain | Required model and invariants |
| --- | --- |
| Units | Property relation, unique property/label pair, bedrooms and integer minor-unit market rent |
| Tenancies | Unit and party relations, unique short code, status `open`/`closed`/`closed_allow_transactions`, dates, rent-review date and nonnegative inspection frequency |
| Rent versions | Tenancy relation, effective date, nonnegative integer minor-unit amount, currency and reason; one version per tenancy/effective date |
| Ledger accounts | Unique installation account code, account type, trust/operating/reserve fund and active flag |
| Journal entries and lines | Entry/line/account relations, currency, effective/posting dates, actor, source and reversal linkage; debit/credit amounts in minor units, exactly one positive side per line, balanced nonempty entries, consistent dimensions and period locks |
| Work orders | Property/unit/tenancy/vendor relations, five states from section 8, priority, quotes, contact and invoice fields; enforced transition guards |
| Audit | Actor/action/entity references, timestamp, request correlation, sanitized changes and canonical hash-chain linkage; append-only writes through the audit plugin |
| Event outbox | Topic, payload and dispatch state persisted in the same domain transaction as the triggering change; idempotent consumer behavior |

The ledger service MUST commit entries and lines atomically, validate all constraints, deny direct application writes, preserve reversals and prevent partial or empty posting. A sample trigger is not proof of these properties. The audit plugin MUST define canonicalization, concurrency-safe chain ordering and independent verification before claiming tamper evidence. Generated roles and UI MUST not expose mutable journal or audit actions. Financial, isolation and recovery checks are release gates, not facts established by generation.

### 11.3 Derived Balances

Balances are never stored. A tenant balance, owner balance or account balance is a sum over `journal_lines` filtered by dimension and fund. For speed, the platform maintains materialized, rebuildable snapshots per period; the nightly verification job recomputes them from the ledger and alerts on any difference.

### 11.4 Data Lifecycle

- Personal data fields are tagged in the schema so export, correction and deletion requests can be automated. Financial records are retained per the retention policy in the rule pack; personal data in them is pseudonymized on erasure rather than the entries being deleted.
- Every table has a documented owner module and a migration policy: forward-only migrations, tested against a snapshot of the previous release.

## 12. API, Webhooks, Plugins and Integrations

### 12.1 Native Resource API

The application uses NocoBase's resource-action APIs and approved plugin actions. Do not scaffold an independent `/v1` backend, authentication service or mobile API. Read actual action names, schemas, pagination and error behavior from the pinned platform and Loom catalog. Tool payloads MUST conform to discovery, not to illustrative domain names in this RFC.

| Concern | Requirement |
| --- | --- |
| Reads and updates | Use native resources with verified role, record and field permissions; qualify concurrency behavior |
| Consequential writes | Plugin actions enforce server-side validation, idempotency, atomicity and approval gates; generic collection CRUD cannot substitute for ledger posting |
| Imports | Dry-run/reconciliation is a required domain capability; use qualified native functionality or an approved gap plugin |
| API documentation | Capture supported native/plugin resource schemas for the pinned release; do not promise unsupported OpenAPI or error conventions |
| Rate limits and audit | Bound integrations per principal and attribute actions; qualify platform behavior and fill documented gaps |
| Upgrade compatibility | Review catalog/schema drift and preserve data with plugin migrations and generation readback |

### 12.2 Authentication and Scopes

Use the selected NocoBase authentication and authorization mechanisms. MFA for financial staff is required before production financial use. Passkeys, federation, OAuth grants and session properties are requirements to qualify or defer explicitly, not assumed CE features. Integrations use separately provisioned principals with minimum native permissions and entity scopes. Loom construction credentials have a distinct lifecycle and never become runtime application credentials.

### 12.3 Resource Map

Section 11.1 lists logical domain resources. Resolve their actual collection/action names and native identifiers into `generation/bindings/` through discovery. Configuration objects (roles, pages, workflows and plugins) also have stable logical IDs and native bindings. Do not invent URL paths from the logical names. Server-only posting, approval and adapter actions MUST expose only their documented narrow contracts.

### 12.4 Webhooks

- Every domain event can be delivered to subscribed endpoints, in a versioned CloudEvents-style envelope.
- Deliveries are signed with an HMAC-SHA256 header that includes a timestamp so receivers can reject replays.
- Failed deliveries retry with exponential backoff for up to 72 hours; the UI shows delivery history, payloads and a manual replay button.
- Event payloads contain identifiers and a small summary, not sensitive documents; consumers fetch details through the API under their own scopes.

### 12.5 Adapter Ports

Each port has a documented interface, a conformance test suite and a fake adapter. The project ships a reference adapter where an open or widely available option exists.

| Port | Purpose | Reference implementation direction |
| --- | --- | --- |
| Payments | Collect rent and fees, pay out owners and vendors | Card and ACH processor adapter (self-hoster supplies credentials) |
| Banking | Transaction feeds and account verification | Account aggregation adapter plus OFX, QIF and CSV import |
| Screening | Credit, criminal, eviction and income reports | Consumer reporting agency adapters |
| E-signature | Signing and completion certificates | Open-source signing service adapter |
| Listings | Syndicate listings and pull inquiries | Portal feed adapters |
| Messaging | Email and SMS delivery | SMTP and an SMS provider adapter |
| Print and mail | Physical notices | Mail service adapter |
| Insurance | Policy verification | Carrier adapters |
| Tax filing | 1099 e-file | IRS IRIS adapter |
| AI | Language models and embeddings | Hosted API adapters and an OpenAI-compatible endpoint adapter |
| Storage | Documents and media | S3-compatible adapter |
| Accounting export | Sync with external bookkeeping tools | Journal export adapters |

ZatiProperty does not become a payment facilitator or money transmitter. Organizations contract with processors directly, which keeps regulatory responsibility with the licensed parties.

### 12.6 Plugins

- A plugin is a package with a manifest declaring its name, version, required permissions, subscribed events, settings schema and extension points.
- Extension points: adapters for any port, report definitions, automation actions, custom field types, rule packs and UI panels on entity pages.
- Native plugins run under NocoBase's actual plugin trust model; permission labels do not establish process isolation. Install only reviewed code. External integration services may use scoped native APIs/webhooks, but an out-of-process or WebAssembly sandbox is not a platform guarantee.
- Installing a plugin requires an organization admin to approve its requested permissions. The audit log attributes every plugin action to the plugin.

### 12.7 Import and Export

Data portability is a core promise. A full export (structured data, documents and ledger) is available at any time in open formats. Importers accept CSV templates and documented mappings so organizations can migrate in from spreadsheets and other systems, with a dry-run and a reconciliation report comparing imported balances to source balances.

## 13. Security, Privacy and Compliance

ZatiProperty holds identity documents, bank details, credit reports and client money. Security and compliance are design constraints, not later features.

### 13.1 Roles and Access Control

Access is role-based and scoped to entities (portfolio, property, owner or tenancy). A user may hold different roles in different scopes. Default roles:

| Role | Scope of access |
| --- | --- |
| Organization admin | Settings, users, roles, integrations, plugins; no ledger posting by default |
| Property manager | Assigned portfolios: tenancies, leasing, maintenance, messaging, approvals |
| Leasing agent | Prospects, listings, applications, showings, lease drafting for assigned properties |
| Accountant | Ledger, banking, reconciliation, fees, distributions, reports, tax forms |
| Maintenance coordinator | Requests, work orders, quotes, vendors, inspections |
| Auditor | Read-only access to ledger, audit log and reports |
| Owner | Own properties: statements, dashboards, approvals, documents |
| Tenant | Own tenancy: balance, payments, lease, requests, messages, documents |
| Vendor | Own assigned jobs, quotes, invoices, messages |
| Service account and AI agent | Explicit scopes only; never granted ledger-posting or decision permissions |

Separation of duties is enforced: the person who creates a distribution run cannot approve it, and a user cannot approve their own manual journal entry.

### 13.2 Security Controls

- **Transport and storage.** TLS 1.2 or later everywhere; encryption at rest for the database, backups and object storage; per-installation data keys behind a key management interface.
- **Sensitive fields.** Government ID numbers, bank account details and screening reports use field-level encryption, are masked by default in the UI and require a reason code to reveal, which is logged.
- **Cards.** The platform MUST NOT store card numbers or security codes. Card entry uses the processor's hosted fields so the deployment stays in the lightest PCI DSS scope.
- **Authentication.** Multi-factor authentication is required for staff roles with financial permissions; passkeys are supported; sessions are revocable.
- **Application security.** Parameterized queries only, output encoding, CSRF protection, SSRF-safe webhook delivery (blocks private address ranges), strict content security policy, upload scanning and type validation.
- **Supply chain.** Pinned dependencies, automated vulnerability scanning, a software bill of materials and signed release artifacts and container images with each release.
- **Backups and recovery.** Documented backup schedule, point-in-time recovery, and a tested restore procedure; recovery objectives are stated in the operations guide.

### 13.3 Privacy

- Collect the minimum personal data needed for each workflow; screening data is collected only after consent and purged on schedule.
- Subject access, correction and deletion requests are supported by schema-level data tagging and an admin workflow; financial records are pseudonymized rather than deleted where law requires retention.
- Consent records (electronic transactions, screening authorization, SMS opt-in, marketing) are stored with timestamp, text version and source.
- Because deployments are self-hosted, data residency is determined by the operator. The project publishes a data-flow map and a template data processing addendum.

### 13.4 Regulatory Map

This table lists topics the design addresses. It is a starting point for operators and their counsel, not legal advice. Rules vary by state, county and city, and change over time.

| Area | Why it matters | Design response |
| --- | --- | --- |
| Fair housing law (federal, state, local) | Prohibits discrimination in advertising, screening and terms | Ad-language checks, uniform written criteria, no protected-class data in AI decisions, audit of criteria applied |
| Fair Credit Reporting Act | Governs use of consumer reports, consent and adverse action notices | Authorization capture, adverse action workflow, secure report storage and purge |
| Equal Credit Opportunity Act | Applies where credit-like decisions use credit information | Reason codes recorded for declines |
| State trust accounting and licensing | Rules for holding client funds and reconciliations differ by state | Enforced trust controls (section 9.2) plus state rule packs for reconciliation cadence and record retention |
| Security deposit laws | Limits, separate accounts, interest, return deadlines and itemization | Deposit ledger, rule-pack timers, itemized deduction statement |
| Rent increase and late fee limits | Caps and notice periods vary by jurisdiction | Rule-pack checks before renewal offers and fee assessment |
| ESIGN Act and UETA | Conditions for valid electronic signatures | Consent capture, audit certificate, tamper-evident hash |
| NACHA rules | Governs ACH origination, authorization and returns | Authorization records, return handling, adapter-level controls |
| PCI DSS | Card data security | No card data stored; hosted payment fields |
| TCPA and CAN-SPAM | Consent and opt-out for texts and email | Consent store, opt-out handling, quiet hours |
| IRS information return rules | 1099 thresholds, forms, deadlines, filing method | Versioned tax rule packs, IRIS adapter, correction workflow |
| GDPR, CCPA and similar | Rights over personal data | Data tagging, export and erasure workflows |
| Accessibility (WCAG 2.2 AA) | Public sites and portals must be usable by everyone | Accessibility checks in CI for web and portals |
| Breach notification laws | Timelines for notifying affected people | Incident response runbook and templates |

**Rule pack governance.** Each rule in a pack records its jurisdiction, effective dates, source citation, reviewer and test cases. Packs are versioned and released independently of the core. Packs for new jurisdictions are community contributions that need review by someone with local expertise before they are marked verified.

### 13.5 Threat Model Highlights

| Threat | Mitigation |
| --- | --- |
| Payout redirection fraud (attacker changes an owner's or vendor's bank details) | Verification step, cool-off period before new details receive funds, notification to previous contact, dual approval on first payout |
| Insider fraud or error in distributions | Dual control, anomaly alerts on unusual amounts and new payees, immutable ledger |
| Owner, tenant or vendor reads another party's records | Native role/data/field scopes, scoped credentials and automated allowed/denied access checks through API, MCP and reports |
| Prompt injection through tenant messages or documents | Untrusted-data handling, no tool execution from data, no AI tools with financial or decision authority |
| Malicious or compromised plugin | Reviewed source/dependencies, explicit installation authority, trusted native plugin boundary, audit attribution and recovery plan |
| Webhook abuse (SSRF, replay) | Address filtering, signed timestamps, per-endpoint rate limits |
| Credential stuffing and account takeover | MFA, passkeys, rate limiting, breached-password checks, login anomaly alerts |

## 14. Deployment, Operations and Quality

### 14.1 Single-Company Deployment

Deploy one qualified NocoBase CE application instance, one PostgreSQL database, a private file store and a TLS proxy per company. Loom is a separately managed construction bridge with scoped credentials and disabled-by-default authoring endpoints. Container/image versions, plugin versions, backup tooling and persistent volumes must be pinned and qualified. Generation preparation does not provision or deploy any of these components.

Cluster mode, horizontally scaled app workers, shared multi-company hosting and a Kubernetes chart are outside this baseline; do not introduce them through inherited standalone architecture assumptions. Air-gapped operation is conditional on all required platform, model and adapter capabilities being qualified locally. It is not a release promise.

Infrastructure secrets use an operator-managed secret store or environment references. Application settings live in native configuration and versioned desired state. Plugin migrations preserve data and require tested backup/restore and upgrade procedures; zero-downtime upgrades are not assumed.

### 14.2 Observability

- OpenTelemetry traces, metrics and structured logs with request, installation and actor identifiers on every line.
- Health and readiness endpoints; a status page in the admin UI showing job queue lag, webhook failures, adapter health and last successful bank sync.
- Service indicators that matter to this domain: payment posting latency, scheduled job lateness, webhook delivery success rate, unmatched bank transactions, and ledger verification results.
- A failed ledger or audit-chain verification is a paging-severity alert by default.

### 14.3 Initial Performance Targets

These are starting targets to be validated by benchmarks in the first release cycle, not guarantees.

| Scenario | Target |
| --- | --- |
| Interactive API reads at 10,000 units | 95th percentile under 300 ms |
| Monthly charge generation for 10,000 tenancies | Under 5 minutes |
| Distribution run draft for 1,000 owners | Under 10 minutes |
| Owner statement PDF generation | Under 5 seconds each, parallelizable |
| Webhook first delivery attempt | Within 30 seconds of the event |

### 14.4 Testing Strategy

| Layer | Approach |
| --- | --- |
| Unit | Domain logic with no I/O; the ledger package has no dependencies beyond the language runtime |
| Property-based ledger tests | Randomized sequences of payments, refunds, reversals, fees and distributions must always satisfy: entries balance, no owner goes negative, trust equals the sum of sub-ledgers, idempotent replays change nothing |
| Adapter contract tests | Every adapter passes its port's conformance suite against its fake and, where available, a provider sandbox |
| Isolation tests | Automated allowed/denied attempts across staff, owner, tenant and vendor scopes through native APIs, runtime MCP and reports; no cross-company RLS model |
| End-to-end flows | Scripted journeys: inquiry to signed lease, rent payment to distribution, request to paid work order, year-end 1099 run |
| Migration tests | Every migration runs against a dump of the previous release with data fixtures |
| Security | Static analysis, dependency scanning, dynamic scanning of a staging deployment, fuzzing of import and webhook endpoints |
| Accessibility | Automated checks plus manual audits of key portal flows |
| AI evaluations | Offline suites for classification, extraction and safety; fair housing red-team cases; regression gates |
| Rule packs | Each rule has fixtures with expected outcomes and a citation |

Required checks are scoped to the affected implementation and recorded against an exact revision. Financial and security implementation requires independent review and domain checks before release. This workflow-only revision does not create an app, run financial tests, or close live generation acceptance.

### 14.5 Developer and Operator Experience

- A qualified fixture workflow uses Loom to populate one synthetic demo company with properties, tenancies, history and ledger fixtures; it never seeds customer or live financial data implicitly.
- Documentation site with quickstart, operator guide, API reference generated from OpenAPI, adapter and plugin authoring guides, and a rule pack contribution guide.
- Public roadmap, issue templates, and a labeled set of good first issues for each module.

## 15. Phased Roadmap

Delivery is organized in four phases, each closed by a gate. A gate is a set of verifiable criteria; the next phase's feature work does not ship as stable until the gate passes. Durations are indicative and depend on contributor capacity.

| Gate | Scope and required evidence |
| --- | --- |
| Gate 0: generation readiness | Pinned CE/license/entitlement evidence, approved target and construction authority, complete current Loom discovery, desired-state and ownership conventions, documented capability gaps. This revision prepares the workflow only; the live gate remains open. |
| Phase 1: foundation | Loom-generated company settings, roles, property/tenancy model and native pages; persistence and denied-access evidence; server ledger/audit invariants qualified before any financial use |
| Phase 2: operational loop | Leasing, maintenance, charges and approvals generated and read back; native journeys and scoped role tests; synthetic adapters before separately authorized provider tests |
| Phase 3: finance and integrations | Reconciliation, distributions, statements, tax/rule packs and external adapters; financial invariants, recovery, independent review and jurisdiction/provider qualification |
| Phase 4: runtime AI and release | Separately scoped runtime AI/MCP, evaluations, complete domain coverage, accessibility, operator restore/upgrade evidence and explicit production acceptance |

Every gate distinguishes implemented source, Loom state readback, native UI acceptance and live provider/production evidence. A planned capability remains open until its required evidence exists.

### 15.1 Release and Stability Policy

- Releases follow semantic versioning. The project stays at 0.x until the API and ledger schema are declared stable at the end of phase 3.
- During 0.x, ledger and audit table structure changes only through migrations that preserve every posted entry; no release may require re-posting history.
- Security fixes are backported to the latest two minor releases.

### 15.2 Deliberately Deferred

These are out of scope for the first four phases and can be proposed as separate RFCs: commercial-property features such as CAM reconciliation and percentage rent, student and short-term rental workflows, construction and capital project budgeting, a native desktop client, and tax regimes outside the United States.

## 16. Risks, Open Questions and Appendices

### 16.1 Risks

| Risk | Impact | Mitigation |
| --- | --- | --- |
| Legal variation across jurisdictions | Wrong late fee, notice or deposit handling exposes operators | Versioned rule packs with citations, community review by local experts, clear not-legal-advice language, warnings over silent automation |
| Ledger defect | Misstated owner balances or trust shortfall | Double-entry invariants in the database, property-based tests, nightly verification, reversing-entry corrections, dual control on distributions |
| Regulatory exposure around money movement | Project could be seen as handling funds | Processor and bank adapters only; operators hold their own accounts and licenses |
| Contributor capacity versus scope | Stalled or shallow modules | Phase gates, a stable core first, modules owned by named maintainers, deferral list |
| Misconfigured self-hosted installs | Data exposure | Secure defaults, configuration linter, hardening guide, backup and restore checks in the admin UI |
| AI misuse in fair-housing-sensitive flows | Discrimination claims and harm to applicants | Autonomy levels, prohibited tools, evaluation gates, applicant-facing AI limited to criteria-based checks |
| Third-party interface changes (portals, screeners, banks) | Broken integrations | Ports with contract tests, adapter versioning, community adapter maintainers |
| Intellectual property overlap with commercial products | Legal or reputational risk | Original design from public feature categories; no copied names, text, UI or assets; contributors attest to originality in the DCO |

### 16.2 Open Questions

The use of Loom MCP, native NocoBase CE, a single company per install and the absence of a standalone app are settled construction decisions. Remaining questions are qualification work:

1. Which exact NocoBase release, CE plugins and Loom revision form the initial supported baseline, and what licenses permit distribution and external stakeholder use?
2. Which owner-approved instance and environment will generation target, with which endpoint, role, catalog and operation scope?
3. Which required capabilities are exposed by that catalog, and which need an upstream Loom extension or documented CE/domain plugin?
4. Which native mobile layouts, file privacy/storage engines, background jobs and security capabilities pass the required checks?
5. Which US jurisdictions receive reviewed trust, deposit, notice and tax rule packs first?
6. Which payment, banking, screening and signing providers will be qualified under separately authorized credentials and sandbox/live scopes?
7. Which runtime AI/MCP features are available and permitted in the pinned CE release? They remain disabled or unqualified until separately scoped and tested.
8. What operator recovery objectives and maximum single-instance workload can the qualified deployment sustain?
9. What governance and original-plugin license decisions need ratification before distribution?
